# 化学实验室

化学实验室是面向 12–18 岁学习者的自由组合式化学实验沙盒。学生把任意物质放进烧杯、任意搭配反应条件，由 Agent 现场裁决会发生什么；产物可以加回材料库，继续往下合成。

作者：Rony Yuan

## 1. 为什么这里必须用 Agent

Na+Cl₂、Fe+CuSO₄、Cu+浓硫酸（加热）、N₂+H₂（高温+加压+催化剂）…… 组合是爆炸的，不可能用规则表穷举。这个 Demo 的分工是固定的：

| 谁来做 | 负责什么 |
|---|---|
| 前端（本地，秒回） | 材料库、容器、条件选择、矛盾提醒、探索目标判定、星级、实验记录 |
| Agent · 反应裁决 | 这个组合在这套条件下会不会反应、产物是什么、现象是什么、原理是什么 |
| Agent · 实验助手 | 陪学生对话：听他的猜测并追问理由、解释原理、帮他定位为什么做不出来 |

关键边界：**Agent 只描述发生了什么，从不授予进度**。探索目标和星级完全由本地 `src/core/quests.js` 根据权威实验台状态判定，模型无法凭一句话给学生解锁目标。

## 2. 实验助手：为什么是对话而不是打分

早期版本是一个「动手前先猜一猜」输入框：点「开始反应」时顺带把猜测发出去，模型回一句 real／half／rote 三档评语，然后就结束了。问题是它**只有一轮** —— 学生被评判完就没有下文，说不清的地方也没机会追问。

现在改成常驻对话框（`/api/demo/chemistry-lab/chat`）：

- **带实验台上下文**：当前烧杯里有什么、条件是什么、上一轮的判定结果，都随消息发过去，所以可以直接问"这样会怎样""刚才那个为什么冒泡"。
- **带对话历史**：最多 12 轮，学生可以追问下去。历史里不含当前这句（服务端单独作为 `message` 接收）。
- **有问必答**：问温度就给温度，问催化剂就给名字，问原理就讲清楚。先给答案，再补原理。
- **纠正误解**：写下猜测时，助手会直接说对不对、错在哪，而不是不痛不痒地附和。

早先这里有一条"不泄露答案"的边界：具体温度和催化剂名不许直说，`chem_contract._strip_answers`
还会在服务端把回复里的 `170℃` 改写成"某个特定温度"、把"二氧化锰"改写成"某种特定催化剂"。

**这条设计已经删掉了**，因为它是错的：

- 生成后再做查找替换分不清"提示"和"解释"，所以它连"水在 100℃ 沸腾"这种通识也一起涂掉，
  学生看到的是"水在某个特定温度沸腾"，助手像坏了一样。
- 主动提问本身就是学习行为，惩罚它没有道理。学生张嘴问了，就是想学这个知识点。
- 语气该点方向还是该给数值，属于 prompt 的事，不该由一段正则在成品句子上做手术。

现在只保留一条真正的边界：**助手不替实验台发进度**（不说"你完成了目标"），
以及危险品制备方法不给可操作细节。其余化学问题一律正面回答。

对话保存在本地，刷新不丢，可单独清空而不影响实验记录。

## 3. 条件模型：为什么温度必须是数字

第一版只有 5 个温度档（常温/加热/高温/点燃/低温）。这表达不出 140℃ 和 170℃ 的区别，于是乙醇＋浓硫酸这类**温度选择性反应永远做不成** —— 模型只能回答"温度不明确"，而且它是对的：条件模型的表达能力不够，不是模型的错。

现在条件沿真实化学依赖的维度建模（`src/core/conditions.js`）：

| 维度 | 取值 | 为什么需要 |
|---|---|---|
| 温度 | 9 个预设档 **＋ 精确摄氏度**（−50…3000，可输入或拖动） | 乙醇脱水 140℃→乙醚、170℃→乙烯，差 30℃ 就是两种物质 |
| 催化剂 | 具名：铁触媒 / V₂O₅ / MnO₂ / 铂铜 / 浓硫酸 / 酶 / 氧化铝 | 合成氨必须用铁触媒，SO₂ 氧化必须用 V₂O₅，**不能互换** |
| 环境 | 干燥 / 水溶液 / 隔绝空气 / 熔融态 / 酸性 / 碱性 | 电解 Al₂O₃ 必须熔融，水溶液里产物完全不同 |
| 压强 | 常压 / 加压 / 减压 | 合成氨、SO₂ 氧化需要加压 |
| 配比 | 适量 / 某种过量 / 氧气不足 / 氧气过量 | C+O₂ 氧足→CO₂、氧不足→CO |
| 附加 | 通电 / 光照 / 研磨 / 搅拌 / 回流 / 边反应边蒸出 | 电解靠通电；酯化靠蒸出产物推动可逆反应 |

三条设计规则：

1. **没设置的维度不发给模型**，因此模型能说"还缺一类条件"，而不是替学生假设一个默认值。
2. **给了精确温度就必须按这个温度判**，落在哪个窗口就给哪个产物，不允许再回答"温度不明确"。
3. **提示要给得动**。`missing` 说清还缺哪一类条件，`hint` 直接说出该试哪个温度、该用哪种催化剂
   —— 学生卡住时"换个方向试试"这种话没有任何用，给出数值让他去验证结果才有用。

选中已知对条件敏感的材料组合时，实验台会主动提示这一组"换个温度产物就不一样"。

## 4. 统一启动

生产和日常联调都使用 WeSmartFlow 的一套前后端，不需要单独启动实验室的 Agent 服务。

### 启动后端

```bash
cd backend
cp .env.example .env
# 编辑 .env 中的 LLM_API_KEY、LLM_BASE_URL、LLM_MODEL
conda run --no-capture-output -n agent zsh -c 'set -a; source .env; set +a; exec python main.py'
```

### 启动主前端

```bash
cd frontend
npm install
npm run dev
```

`predev` 会自动构建本主题到 `frontend/public/chemistry-lab/`。访问：

```text
http://localhost:5173/#/explore
http://localhost:5173/chemistry-lab/index.html?source=wesmartflow
```

## 8. 运行链路与 API

页面只请求相对 API：

```text
POST /api/demo/chemistry-lab/react        判定一次组合
POST /api/demo/chemistry-lab/chat         与实验助手多轮对话
GET  /api/demo/chemistry-lab/health       探活
```

挂载链路：

```text
backend/main.py
└── backend/routers/examples.py
    └── backend/routers/chemistry_lab.py
        └── chemastry_lab/chemistry_lab_api.py:router
```

后端执行输入安全检查、频率限制、结构化模型调用，再由 `chem_contract.py` 把模型输出裁剪成页面能渲染的形状：

- 反应类型、产物状态、条件判定只能取枚举值；
- `cond_check` 只能回报学生**实际选过**的条件，模型不能凭空追加一个条件；
- 产物化学式必须是纯化学式，否则不允许进入材料库；
- 触发安全红线时强制 `reacts=false` 并清空方程式与产物；
- 声称反应却给不出方程式时，判定被降级为「没算出来」，而不是渲染一个假结论。
- **不许拿「超纲」当不反应的理由**。`reacts` 回答的是客观化学事实，只能由化学决定。
  曾经出现过这样的判定：

  > 常温、隔绝空气下，AlCl₃、CH₃Cl 和 C₆H₆ 三者互不反应。……该反应属于大学有机化学范畴，
  > 中学范围内不要求掌握，故判断为不反应。

  这是错的：傅-克烷基化真实存在（`C₆H₆ + CH₃Cl --AlCl₃--> C₆H₅CH₃ + HCl`），
  而"隔绝空气"恰好满足它需要的无水条件。超纲只意味着学生不必背，不意味着反应不发生 ——
  这样答会让他记住一个假事实，比承认"算不出来"糟得多。

  两道防线：prompt 明确禁止这条推理，并要求超纲反应照常给方程式、把 `scope` 标为 `"超纲"`；
  服务端 `chem_contract._blames_syllabus` 兜底 —— 当"不反应"的理由里同时出现超纲措辞
  （超纲／大学有机／不要求掌握…）和因果措辞（故／因此／判断为…）时，判定被降级为
  「没判定出来 · 可重试」。只有两者**同时**出现才拦，所以"反应了但顺带说明这属于大学内容"
  不受影响。日志关键字：`used the syllabus as the reason for no reaction`。

  超纲反应在结果卡上显示一行说明：反应是真的、方程式是对的，只是课本不要求掌握。
- **方程式必须配平**：`equation_check.py` 会逐原子重新数一遍两边的原子数，不相等就丢弃整个判定。
  学生看到的是「这一轮没算出来 · 可重试」，并明确说明"这不代表它们不反应"，这条记录也不进实验记录、不推进目标。
  只有**可证明不配平**的才拒绝；含"石蕊"这类占位试剂、聚合物下标 `n`、离子电荷等本模块不建模的写法一律放行，
  避免误杀正确判定。判定依据可在后端日志中查到（`Rejected an unbalanced equation`）。

可调后端环境变量：

| 变量 | 默认值 | 作用 |
|---|---:|---|
| `CHEM_LAB_AGENT_RPM` | `20` | 每 IP 每分钟请求上限，范围 1–120 |
| `CHEM_LAB_LLM_TIMEOUT` | `60` | 单次模型请求超时秒数，范围 10–120 |
| `CHEM_LAB_THINKING` | `on` | 推理**默认值**，设 `off`／`0`／`false` 改为默认关闭 |
| `CHEM_LAB_THINKING_TOKENS` | `4096` | 深度推理模式的 `max_tokens`，范围 256–32768 |
| `CHEM_LAB_VERDICT_TOKENS` | `1024` | 快速模式下判定的 `max_tokens` |
| `CHEM_LAB_CHAT_TOKENS` | `1280` | 快速模式下对话的 `max_tokens` |

三个 `*_TOKENS` 设的是**第一次尝试**的额度；解析失败重试时自动放宽到 4/3
（因为首次失败最常见的原因就是额度用尽）。代码里对应
`chemistry_lab_api.py` 的 `REASONED_BUDGETS` / `OUTPUT_TOKEN_BUDGETS` /
`CHAT_TOKEN_BUDGETS`，每个元组是**一次请求的两次机会**，不是两种用途。

若日志里频繁出现 `hit the N-token ceiling before finishing the JSON`，
就是额度不够，调大 `CHEM_LAB_THINKING_TOKENS` 即可。

### 推理开关（页面右上角）

`CHEM_LAB_THINKING` 只决定默认值，页面上可以随时切换，**不需要重启后端**：

| | 深度推理 | 快速模式 |
|---|---|---|
| 判定预算 | 3072 → 4096 | 1024 → 1280 |
| 对话预算 | 3072 → 4096 | 1280 → 1536 |
| 配平可靠性 | 高 | 复杂反应容易配错被丢弃 |
| 单轮耗时 | 明显更长 | 短 |

链路：`ReactionRequest.thinking` / `ChatRequest.thinking` 是三态的
`bool | None` —— `null` 表示"用服务端默认"，`true`/`false` 表示本次请求覆盖。
`_thinking()` 决定实际模式，`_budgets()` 把 token 预算和模式绑在一起
（推理 token 和答案共用 `max_tokens`，只翻开关不放预算会让 JSON 中途被截断）。

前端的三个状态与之对应：偏好存在 `chemistry-lab:thinking`（**独立于进度**，
所以"清空进度"不会顺带重置它）；没存过时显示「推理 · 检测中」，
待 `/health` 返回 `thinking` 字段后采用服务端默认；学生自己点过之后，他的选择优先。

两处配套体验：判定被配平校验丢弃时，如果当时是快速模式，结果卡会直接提示
"切到深度推理再试一次"；等待文案也分模式 —— 快速模式下等超过 20 秒才提醒可以开推理，
而不是笼统地让人再等。

### 为什么默认开着 thinking

配平的本质是逐元素数原子，这正是关掉推理就会崩的那类工作。早先这里写死
`thinking: {"type": "disabled"}`，理由是"判定只是一小段 JSON，省掉推理更快"，
但实际形成了一个负反馈：模型凑系数 → `equation_check` 逐原子核对后拒绝 →
学生等满一轮只看到「这一轮没算出来」→ 重试。**一次想清楚比错三次再重试更快。**

预算不够的表现是 JSON 在中途被截断。这种情况在日志里单独记一行
（`hit the N-token ceiling before finishing the JSON`），以便和"模型不遵守 schema"区分开。

前端超时相应提到 150s（`src/core/agent-limits.js`）：服务端单次 60s 且会重试一次，
最坏约 120s，浏览器必须等得比它久 —— 否则前端先放弃，而后端还在继续算，
这是唯一纯亏的结局。

### 慢 ≠ 离线

化学判定常需要模型思考较久，因此前端严格区分三种失败：

| 情况 | 表现 | 状态灯 |
|---|---|---|
| 超时 | 提示这一轮太慢，可直接再点一次 | 保持在线 |
| HTTP 错误 | 显示状态码，提示看后端日志 | 保持在线 |
| 连不上 | 提示确认后端在跑 | 标为离线，可点灯重连 |

任何一种失败都不会伪造判定结果，也不会丢掉已有的实验记录。

## 9. 进度与兼容

进度保存在浏览器：

```text
localStorage: chemistry-lab:progress:v3
sessionStorage: chemistry-lab:wesmartflow-entry
```

保存内容为实验记录、合成出来的材料、已完成的探索目标和与实验助手的对话。每条记录还带材料指纹和条件文本，用来判定"同一组材料换个温度得到了不同产物"。实验记录面板底部提供显式清空入口，只删除本主题的键，不影响其他探索主题；对话框底部另有单独的"清空对话"，不会连带删掉实验记录。

`v2` 加入了材料指纹字段，`v3` 用对话记录替换了一次性猜测计数。`v1`／`v2` 的旧进度会被自动迁移而不是丢弃：旧记录无法满足"同料不同温"这一个目标，而 `v2` 里已写过猜测的学生会直接获得"把想法说出来"，不会丢掉已拿到的星。修改存储结构时应继续升级版本并保留迁移。

响应式与无障碍约定：

- `ui-scale.css` 提供 `100vh` 回退，在支持时切换到 `100dvh`，并处理 `env(safe-area-inset-*)`；
- 1080px 以下结果与目标区转为自适应多列，760px 以下单列，360px 无横向溢出；
- 材料既可拖拽也可「点材料再点烧杯」，不依赖拖拽或 hover；
- 烧杯里的移除按钮在触屏上常驻可见，不依赖 hover 才出现；
- 所有可操作元素都是真实 `button`，可键盘聚焦，单选/多选条件带 `aria-pressed`；
- 尊重 `prefers-reduced-motion`：关闭气泡与抖动，反应状态仍由颜色、符号和文字表达。

## 10. 新增探索目标

目标是声明式的，只需在 `src/core/quests.js` 的 `QUESTS` 里加一条：

```js
{
  id: "your-goal",              // 全局唯一，进入 localStorage
  label: "12",
  title: "目标标题",
  detail: "一句话说明要做到什么",
  check: ({ reaction, held, conditions, progress }) => /* 布尔判定 */,
}
```

`check` 只读权威实验台状态和已归一化的判定结果：`reaction` 是裁剪后的结果，`held` 是烧杯里的物质，`conditions` 是学生设置的条件（可用 `tempPreset(conditions)` 判断他是否填了精确温度），`progress` 是历史进度。星级阈值按目标总数自动换算，不需要另外改动渲染代码。

`check` 只读权威实验台状态和已归一化的判定结果，星级阈值会自动按目标总数换算，不需要另外改动渲染代码。

## 11. 提交前清单

- 空烧杯、单一物质、五种物质三种情形都不会报错；
- 乙醇＋浓硫酸在 140℃ 与 170℃ 下给出不同产物（乙醚 / 乙烯）；
- 只选温度档位而不填精确温度时，提示需要更精确的温度，并直接给出该试的数值；
- 合成氨用错催化剂被判为不反应，换成铁触媒并加压后成功；
- 浓硫酸与稀硫酸能同时在库中区分，且不会被误判为同一条目；
- 产物加回材料库后可用于下一次反应，不会刷出重复条目；
- 目标解锁与星级只由本地判定，Agent 无法凭回答直接给分；
- 实验助手能多轮追问，问具体温度和催化剂时给出明确答案，不推脱；
- 不配平的方程式被拒，页面显示「没算出来」而非「不反应」，且不写进实验记录；
- 助手回复里的温度数值与催化剂名称原样呈现，不会被过滤成占位词；
- 后端不可用时有明确降级提示，且不伪造反应结论；
- 对话失败不会清掉已有对话，「清空对话」不会连带删除实验记录；
- 刷新后实验记录、对话与目标进度可恢复，清空只影响本主题；
- `npm run validate:examples` 和主前端 `npm run build` 全部通过；
- `python -m pytest examples/chemastry_lab/test_equation_check.py` 全部通过；
- 源码中没有 `dist/`、`__pycache__/`、日志、截图或真实密钥。
